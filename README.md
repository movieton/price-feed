# Генератор фида цен

Полная документация проекта: [wiki генератора](docs/wiki/README.md).

Локально готовый генератор на Python 3.9+ (для сервера рекомендуется поддерживаемый Python 3.11+), только стандартная библиотека. Без БД, Docker и внешнего хостинга. Linux для установки с systemd; локальные тесты работают на macOS/Linux. Исходная рабочая папка была пустой, существующего приложения для интеграции не было.

Формат взят из `examples/feed-template.xml`, копии предоставленного файла. Это не формат Google/Meta. Валидность XML и соответствие образцу **не подтверждают приём КИП**: нужна тестовая загрузка или подтверждение КИП. Подключение к Routes&Roads проверено с доступом только `read_products`; товары, остатки, тема и настройки магазина не изменялись. На сервер проект пока не устанавливался.

## Локальная демонстрация

Из папки проекта:

```sh
python3 -m unittest discover -s tests -v
python3 feed.py --config config.example.json --fixture examples/catalog.jsonl
```

Результат: `runtime/public/feed.xml`. Копия демонстрационного результата включена в `examples/generated-feed.xml`. Вход: один тестовый товар с двумя вариантами; остатки 5 и 0. `--fixture` полностью отключает обращение к Shopify. Все примеры содержат вымышленные данные. Пути в JSON разрешаются относительно текущей рабочей папки; на сервере используйте абсолютные пути.

Код выхода 0 означает успешную замену фида; 1 — отказ обновления. JSON-строка в stdout содержит UTC-время, длительность, количество товаров/вариантов, сформированных offers, отфильтрованных вариантов, пропуски и причины. До 100 проблемных variant ID выводятся для диагностики; полные тексты API-ошибок и названия товаров не журналируются.

Для одноразовой подготовки локальной карты категорий по реальным `productType` после Bulk-выгрузки используется `scripts/build-local-config.py`. Он создаёт игнорируемый Git файл `config.local.json`, а идентификатор каждой категории стабильно вычисляет из точного названия типа товара. Пустой тип не заменяется вымышленным значением: соответствующий вариант будет пропущен. Скрипт не читает и не записывает секреты.

Контрольный запуск 8 сентября 2026 года прочитал 1 174 активных товара и 1 537 вариантов, сформировал 1 461 offer и пропустил 76 вариантов с отсутствующими или некорректными обязательными данными. Результат сохранён локально как `runtime/public/price-feed.xml`; каталог `runtime` не попадает в репозиторий.

## Согласованные и ожидающие решения

Фид предназначен для прайсмониторинга. Отсутствие обязательных данных исключает только соответствующий вариант (offer), остальные предложения и их цены продолжают обновляться. Если отсутствует общее поле товара, исключаются все его затронутые варианты. Причины и количество пропусков записываются в журнал. В образце общий минимум — `offer@id` и `name`, `category@id` и текст категории; комментарии отдельно требуют хотя бы одну категорию и картинку. По дополнительному требованию в каждый offer добавлен код валюты `currencyId`. Поэтому здесь обязательны `id`, `name`, `url`, положительная `price`, `currencyId`, `categoryId`, `picture`; категория должна существовать. Это рабочий профиль проверки предложений, не независимая спецификация КИП. Состав обязательных полей сохранён; изменена обработка пропусков.

Перед реальным запуском заполнить и подтвердить:

- `shop_domain`: точный `*.myshopify.com` домен.
- `market`, `country`, `currency`: активный рынок, страна и ожидаемая валюта.
- `price_mode`: `base` (обычная цена в валюте магазина) либо `market` (contextualPricing для страны). Нет ручной конвертации, сравниваемой цены или расчёта скидок.
- `language`: основной язык магазина. Сейчас поддержан только `language_mode: primary`, поля Shopify используются дословно. Переводы не подставляются автоматически. Для другого языка сначала добавить и проверить явное извлечение переводов, иначе запуск заблокирован.
- `catalog_query`, `product_statuses`: состав каталога. Пример `product_status:active` выбирает активные товары через фильтр вариантов, повторная проверка статуса выполняется локально. Наличие onlineStoreUrl обязательно; доступность товара в конкретном рынке сама по себе не проверяется. Для рыночного ассортимента нужно согласовать точный фильтр (например, подготовленный тег) и сверить его с каталогом рынка.
- `availability_confirmed`: подтверждение правила ниже; не включать, если нужны отдельные склады или физический on_hand.
- `categories`, `category_map`: стабильные коды категорий и явное соответствие `productType → category ID`.
- `option_params`: соответствие реальных названий опций параметрам образца; `extra_data`: файл с подтверждёнными параметрами/uuid либо пустая строка. Удалить ссылку на тестовый extra-data перед реальным запуском.
- Сервер: ОС, веб-сервер, домен с TLS, пути и интервал обновления.

После согласования поставить `live_confirmed: true`. По умолчанию реальный запуск заблокирован. Значения EUR/FR и категории в примере — только демонстрация, не выбор для магазина пользователя.

## Отображение данных

| XML | Источник и правило |
|---|---|
| offer@id | Числовая часть Shopify ProductVariant GID; отдельный offer для каждого варианта. Не SKU и не индекс. Удаление и повторное создание варианта меняет ID. |
| offer@uuid | Только переданная связка учётной системы в extra-data; не генерируется. |
| offer@available | inventoryItem.tracked=true и inventoryQuantity>0. Ноль и отрицательное значение → false. Неотслеживаемый или неизвестный остаток → ошибка. |
| name | Название товара + значения опций варианта; стандартный Default Title не добавляется. Размер включается сюда. |
| url | onlineStoreUrl + variant ID, существующие query-параметры сохраняются. Для согласованного рыночного домена/префикса: storefront_base_url + /products/handle + variant ID. |
| price | Decimal без округления через float; только конечное число >0, без валютного символа. |
| currencyId | Трёхбуквенный код из `currency`, например `EUR`; для market-цены должен совпадать с валютой `contextualPricing`. |
| categoryId | Явная карта productType, никакой придуманной категории по умолчанию. |
| picture | Картинка варианта, при её отсутствии главная картинка товара; одна картинка соответствует минимуму образца. |
| vendor / barcode | Исходные поля Shopify; пустые не выводятся, ведущие нули barcode сохраняются. |
| Артикул | SKU варианта; пустой не выводится. |
| Остальные param | Только явные option_params и extra-data с точными названиями из образца. |

Допустимые имена: `Артикул`, `Цвет`, `Пол`, `Возраст`, `Сезон`, `Вид активности`, `Тип товара`, `Модельный год`, `Назначение`. Новый `Размер` не добавляется. Бренд, штрихкод и параметры необязательны; неизвестные значения пропускаются, не угадываются. Конфликт двух источников одного параметра отклоняется. В extra-data ключ — числовой ID варианта, внутри `uuid` и/или `params`; SKU берётся только из Shopify.

**Наличие:** inventoryQuantity — суммарный доступный для продажи остаток, не доказательство физического наличия на выбранном собственном складе. Текущая реализация подходит лишь после подтверждения этого правила. Если Shopify включает остатки поставщиков, либо нужен on_hand определённых locations, потребуется отдельная выборка остатков и проверка правила перед подключением. availableForSale и разрешение продолжать продажи при нуле не используются.

**Рынок:** contextualPricing выбирается по стране, а не произвольному названию market. Для live market режима обязателен `storefront_base_url` (например, подтверждённый HTTPS-домен с языковым префиксом). Это настройка ссылки, а не доказательство цены на витрине: проверить несколько вариантов на соответствие фактической цене, налогам, валюте, ассортименту и языку выбранного рынка. B2B, индивидуальные прайс-листы и скидки корзины не реализованы.

## Shopify: доступ после отдельного согласования

1. Создать/выбрать собственное приложение в Shopify Dev Dashboard и установить на нужный магазин. Это отдельный этап; генератор не создаёт и не устанавливает приложения.
2. Запросить только `read_products` для текущей выборки. InventoryItem допускает `read_products` **или** `read_inventory`; никаких write-scopes не нужно. Если впоследствии потребуется выборка inventoryLevels по складам, отдельно оценить необходимость `read_inventory`/`read_locations`.
3. Для приложения и магазина в одной Shopify-организации задать `SHOPIFY_CLIENT_ID` и `SHOPIFY_CLIENT_SECRET`. Генератор получает токен через client_credentials при каждом запуске; хранит его только в памяти. Такой токен живёт примерно 24 часа. Ограничение принадлежности одной организации существенно.
4. Альтернатива: `SHOPIFY_ADMIN_TOKEN` с действующим offline Admin token, полученным через подходящий OAuth-процесс или существующее приложение. Он имеет приоритет. Для истекающего вручную выданного токена обеспечить обновление; встроенный client_credentials режим решает это только для поддерживаемой организации. OAuth authorization-code/refresh-token процесс для сторонней организации в этот проект не входит.
5. Сохранить секреты **за пределами репозитория**, например `/etc/price-feed/credentials.env`, режим 600. Пример есть в deploy. Не передавать ключ в аргументах команды, не включать shell tracing. JSON-конфигурация не содержит секретов.

В API используется только `bulkOperationRunQuery` — технически GraphQL mutation запуска задачи чтения, не изменения товара. Дальше опрос **собственного ID операции**, скачивание JSONL без Admin-токена в запросе к файловому хранилищу. Redirect отклоняется, чтобы токен не ушёл другому хосту.

API зафиксирован на **2026-04**, запросы проверены встроенным валидатором Shopify этой версии. Он сообщает deprecated для image/featuredImage, пока доступных в выбранной версии. Перед окончанием поддержки версии требуется миграция на media/featuredMedia с обновлением разборщика JSONL и тестов; не переключать api_version вслепую. Подсказка валидатора перечисляет read_products/read_inventory совместно, но документация InventoryItem разрешает любой из этих scopes.

## Установка на существующий Linux-сервер

Это подготовленные инструкции, **на сервере ничего не выполнено**. После согласования администратора:

1. Установить системный Python, если отсутствует; pip-зависимости не нужны. Скопировать проект в `/opt/price-feed`. Проверить тесты на сервере.
2. Создать системного пользователя `pricefeed`. Код держать доступным ему на чтение. Создать `/etc/price-feed` (root, 700), `/var/lib/price-feed` (pricefeed, 700), `/var/www/price-feed` (pricefeed, 755).
3. Скопировать и заполнить конфиг в `/etc/price-feed/config.json`, права 644; родитель `/etc/price-feed` должен разрешать пользователю pricefeed чтение конфига: практический вариант root:pricefeed 750 и config root:pricefeed 640. credentials.env оставить root:root 600: systemd читает его до переключения пользователя.
4. В конфиге поставить `output: /var/www/price-feed/feed.xml`, `state_dir: /var/lib/price-feed`, `extra_data: ""` или абсолютный путь к собственным подтверждённым данным. Все процессы этого фида должны использовать один state_dir и один output.
5. Скопировать service/timer из deploy в `/etc/systemd/system/`. В service при необходимости изменить Python и пути. TimeoutStartSec должен превышать бюджет Bulk + загрузки + повторов.
6. Выполнить один запуск, проверить журнал и файл, затем включить расписание:

```sh
sudo systemctl daemon-reload
sudo systemctl start price-feed.service
sudo journalctl -u price-feed.service -n 30 --no-pager
sudo systemctl enable --now price-feed.timer
systemctl list-timers price-feed.timer
```

Интервал настраивается в timer: `OnUnitActiveSec=1h`, например `30min` или `6h`. После изменения — `daemon-reload` и `restart price-feed.timer`. После перезагрузки запуск через 5 минут; пропущенные часовые запуски не воспроизводятся пачкой. systemd не запускает второй экземпляр активного сервиса, файловая блокировка дополнительно защищает от ручного запуска.

Если systemd отсутствует, использовать **вместо него** cron с тем же рабочим каталогом, config, секретами и единственной блокировкой; для журналов настроить ротацию. Не включать два расписания одновременно. Готовые файлы рассчитаны на Linux/systemd; конкретный способ установки уточняется по серверу.

## Постоянный HTTPS-адрес

В существующий HTTPS server-блок Nginx добавить фрагмент `deploy/nginx-location.conf`, проверить `nginx -t`, затем перечитать конфигурацию. Получится `https://ВАШ-ДОМЕН/feeds/price-feed.xml`. TLS обеспечивает уже имеющийся веб-сервер и его действительный сертификат. Если HTTPS ещё не настроен, сертификат и домен настраиваются отдельно при установке. Не публиковать весь `/opt/price-feed` или state_dir.

Фрагмент разрешает скачивание фида только с исходного IP `5.129.221.173`, который 9 сентября 2026 года соответствует `app.marketing-calendar.ru`, а также с `127.0.0.1` и `::1` для локальной диагностики. Остальные адреса получают `403`. Nginx не проверяет доменное имя удалённого клиента: правило `allow` работает по IP фактического соединения. Если сервис КИП сменит IP или будет обращаться через другой узел, список нужно обновить после подтверждения адреса. Если перед Nginx появится reverse proxy, сначала потребуется корректная доверенная настройка `real_ip`.

Nginx читает только опубликованный `feed.xml`; временный файл записывается рядом, проверяется и заменяет его через os.replace на той же файловой системе. Точный location не открывает временные файлы. При первом неуспешном запуске фида ещё нет — URL отдаёт 404. После успешного запуска при ошибках остаётся прежний файл.

Локально на сервере проверить `curl -I --resolve ВАШ-ДОМЕН:443:127.0.0.1 https://ВАШ-ДОМЕН/feeds/price-feed.xml`: ожидаются HTTPS, 200 и Content-Type XML. С произвольного внешнего IP ожидается 403; успешный внешний запрос нужно проверить со стороны КИП. Сверить скачанный файл с локальным опубликованным и передать КИП на тест. Эта проверка и публикация пока не выполнялись.

## Ошибки и эксплуатация

- При успешной выгрузке смотреть `skipped`, `reasons` и `issues`: варианты с отсутствующими или некорректными данными исключены. После исправления источника они автоматически вернутся при следующем запуске. `required_data_missing_or_invalid` возникает только при явно включённом строгом режиме `missing_policy=fail`. Генератор сам Shopify не меняет.
- `base_currency_mismatch`, `market_currency_mismatch`: проверить валюту и тип цены. Конвертации по догадке нет.
- `unknown_stock`: остаток не отслеживается или отсутствует. Согласовать правило; не приравнивать к true.
- `live_configuration_not_confirmed`: обязательные решения пока не заполнены.
- `http_401`, `oauth_http_401`: токен/секрет/срок действия; `403` — доступ/установка. Тексты ответа скрыты, чтобы не утекли ключи. Проверять доступ через защищённые инструменты администратора.
- `graphql_error`, `bulk_submission_rejected`: проверить запросы из examples, версию API, scopes, фильтр и лимиты Bulk. Ошибки GraphQL не маскируются частичными данными.
- `bulk_timeout_resume_next_run`: ID операции сохранён в state_dir/operation.json; следующий запуск продолжит опрос. При terminal failure state удаляется, partialDataUrl никогда не используется.
- `pending_operation_config_changed`: конфиг запроса изменён при незавершённой операции. Вернуть старый конфиг/дождаться завершения, затем архивировать файл состояния вручную при остановленном расписании. Не удалять state вслепую.
- `bulk_count_mismatch`: неполная выгрузка; не публикуется. Подсчёт строк сверяется с objectCount; текущий запрос не содержит вложенных connections, одна строка = вариант.
- `already_running`: другой процесс держит flock. Старый файл lock после завершения безопасен; удалять его при работе нельзя.
- `too_few_offers` / `offer_count_drop`: используются только при вручную заданных ограничениях. В поставляемой конфигурации `min_offers=0`, `max_drop_fraction=1`: сокращение каталога из-за исключённых предложений не блокирует обновление.
- `ParseError`: недопустимый XML-символ; прежний фид сохранён. `OSError`/`PermissionError`: проверить диск и права.

Повторы ограничены `retries`, экспоненциальной задержкой с jitter, Retry-After и GraphQL throttleStatus; есть сетевой timeout, лимит длительности/размера скачивания и ожидания Bulk. Неоднозначно завершившаяся отправка bulkOperationRunQuery **не повторяется автоматически в рамках запуска**, чтобы не создать дубликаты. После потери ответа задача может остаться на Shopify: при повторных проблемах проверить Bulk jobs приложения. Другие временные HTTP/сетевые ошибки повторяются.

`missing_policy=skip` выбран по умолчанию; `max_skip_fraction=1` разрешает любое количество пропусков. Если после полной успешной выгрузки и проверки данных не осталось корректных предложений, публикуется XML с пустым offers; журнал показывает offers=0 и причины пропусков. Приём пустого фида и значение исчезновения предложения для истории мониторинга нужно проверить с КИП. Дубликаты непустых ID, невалидный XML, сбой API, неполная загрузка или ошибка записи по-прежнему отклоняют обновление и сохраняют предыдущий файл. Изображения и URL проверяются синтаксически; HTTP-загрузка каждой картинки не выполняется.

JSONL читается построчно; дерево конечного XML находится в памяти. Проверен тест 2000 товаров × 3 варианта, без БД. Если каталог сильно вырастет, оценить память и лимит max_download_bytes. Для мониторинга использовать journalctl и проверку возраста feed.xml существующими средствами сервера; отдельного сервиса уведомлений нет. Дата yml_catalog — UTC.

Реальный пробный Bulk-экспорт выполнен для базовых цен EUR, основного французского языка, активных товаров и суммарного отслеживаемого остатка. До эксплуатации остаются установка на сервер, проверка постоянного HTTPS-адреса и тестовый импорт КИП. Правило остатков и состав каталога следует повторно утвердить перед серверным расписанием.
